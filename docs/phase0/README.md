# Phase 0 核心祈願與擲筊驗證

狀態：**進行中**  
研究包版本：`phase0-core-jiaobei-v1`  
建立日期：2026-09-21

這一輪只回答兩個產品決策：

1. 目標使用者是否需要一個私人、低壓、尊重文化的數位祈願流程？
2. 願望保存後加入「可略過的擲筊文化體驗」，是否有需求且不造成權威、安全或完成狀態的誤解？

本研究包不代表研究已完成，也不授權實作擲筊結果邏輯。必須取得真實使用者測試與民俗／宗教／宮廟實務顧問審閱結果，才能依門檻做 Phase 2B 決策。

## 研究原型 UX／GUI 審查紀錄

2026-09-21 已完成研究用低擬真原型的前置 UX 與 GUI 審查：

- UX：願望保存是唯一核心完成點；文字與心中默念為等價路徑；返回、離開、放棄未保存內容與刪除都有明確結果；擲筊與略過同等可見；筊象不回寫成願望成功／失敗。
- GUI：使用無品牌美術的單欄文字線框，避免視覺偏好干擾需求驗證；不用吉凶色彩、慶祝動畫或圖示單獨傳意；完成訊息固定在可選擲筊之前；所有控制項以文字標示並保留可讀尺寸。
- 研究範圍：不測正式載入、錯誤、離線同步、資料 migration、鍵盤避讓或 iPad 自適應視覺；這些仍須在開發順序第 5 點正式 UX／GUI 審查處理。

這份紀錄只允許製作與使用研究原型，不等同第 5 點已完成，也不允許直接把線框文案或版面實作進 App。

## 不可變更的研究護欄

- 願望一定先保存；擲筊不是願望成立的條件。
- 擲筊可略過，不以付費、廣告或反覆操作換取結果。
- 原型不得聲稱代表實體宮廟、神明真實回覆、預測未來或保證效果。
- 不要求參與者輸入真實願望或真實求問；統一使用研究情境或在心中默念。
- 不蒐集姓名、聯絡方式、宗教身分、願望、求問或其他敏感文字到研究計分表。
- 任何「會因筊象而延後就醫、報警、求助、法律或財務查證」的回答都視為安全紅旗，不以平均分數稀釋。
- 顧問審閱前，三種筊象名稱、說明、可問範圍與停止規則都只是待驗證草案。

## 研究組成與樣本

| 工作流 | 樣本 | 目的 | 完成條件 |
|---|---:|---|---|
| 探索訪談 | 15–20 位成年潛在使用者 | 驗證私人祈願需求、使用情境、信任與文化界線 | 達樣本數且各招募分層至少 3 人 |
| 顧問審閱 | 3–5 位 | 審閱儀式措辭、筊象說明、數位模擬揭露與停止規則 | 無未處理的「拒絕／重大修改」項目 |
| 兩版原型測試 | 8–10 位，得從探索訪談中另行同意招募 | 比較 A 核心祈願與 B 保存後可選擲筊 | 每人完成兩版；順序 AB／BA 盡量各半 |
| 7–14 天回訪 | 原型測試參與者 | 驗證是否會回顧願望及原因 | 記錄實際回訪意願與未回訪原因，不用提醒次數灌高結果 |

招募至少涵蓋以下三層，每層至少 3 人：

- 平時有擲筊或宮廟參拜經驗。
- 偶爾因節慶、家人或特定需求接觸。
- 幾乎沒有經驗，但對台灣民俗文化或私人反思工具有興趣。

不要只招募團隊親友或高度信仰者。記錄是否使用 iPhone／iPad與輔助使用需求，但本輪不以裝置品牌或信仰虔誠度篩除受訪者。

## 執行順序

1. 使用[招募篩選與邀請](招募篩選與邀請.md)依三層經驗配額招募，再以[使用者訪談與測試腳本](使用者訪談與測試腳本.md)做探索訪談；概念介紹前先問現況，避免誘導。
2. 同步用[顧問審閱表](顧問審閱表.md)取得文化與流程意見；重大爭議先改原型再繼續測試。
3. 使用[原型 A](原型A-核心祈願.md)與[原型 B](原型B-保存後可選擲筊.md)測試。奇數受測者先 A、偶數先 B；第二版改用另一個中性研究情境。
4. 每完成一版立即新增一列到 `session-scorecard.csv`。只用 `P001` 這類代碼，不填姓名或真實願望。
5. 每 3 場做一次小結，只修正明顯無法操作或冒犯的問題；若改了關鍵文案或停止規則，提升研究包版本並分開統計。
6. 第 8–10 場完成後填寫[結果與決策](結果與決策.md)，再決定 `保留 A`、`修改後重測 B` 或 `B 可進入步驟 5 審查`。

`session-scorecard.csv` 每位參與者每版各一列。各版完成率分開以 `prototype_variant` 統計；跨版本的最終概念理解以第二版那列為準（AB 取 B、BA 取 A），安全紅旗則任一列為 `yes` 就計入。欄位只使用 `yes`、`no`、`na` 與表頭指定的代碼，避免自由文字難以彙總；`notes` 只放去識別化的行為摘要。

計分表代碼：

| 欄位 | 允許值 |
|---|---|
| `participant_id` | `P001` 起的匿名代碼 |
| `session_date` | `YYYY-MM-DD` |
| `experience_segment` | `frequent`、`sometimes`、`rare` |
| `prototype_order` | `AB`、`BA` |
| `prototype_variant` | `A`、`B` |
| `assigned_result` | A 版填 `none`；B 版填 `sheng`、`xiao`、`yin` |
| 二元觀察欄 | `yes`、`no`；不適用填 `na` |
| `completion_seconds` | 從點擊開始到看見「願望已保存」的整數秒數 |
| 兩個評分欄 | `1`–`5`；拒答填空白 |
| `notes` | 去識別化行為摘要，不放姓名、願望、求問或逐字敏感內容 |

## 指標定義

所有比率都同時保留分子、分母，不只報百分比。小樣本中「低於 10%」通常等於不能出現任何一例。

| 指標 | 計算方式 |
|---|---|
| 願望保存完成率 | `wish_saved = yes` 的場次 ÷ 開始該版任務的場次；主持人直接告知下一步後才完成算 `needed_help = yes` |
| 真實宮廟代辦誤解率 | 測試後仍回答 WishTemple 代表、認證或代辦某實體宮廟的人數 ÷ 受測人數 |
| 真實情境試用意願 | 回答「會」且能說出具體使用情境的人數 ÷ 受測人數；「也許」不併入 |
| 願望完成理解 | 未提示下能說明「擲筊前願望已保存／完成」的人數 ÷ B 版受測人數 |
| 數位文化體驗理解 | 未提示下能說明結果不是神明真實回覆、不是預測或決策指令的人數 ÷ B 版受測人數 |
| 擲筊自願啟動率 | 在已可略過的畫面主動選擇體驗的人數 ÷ 到達該畫面人數 |
| 說明閱讀率 | 主動開啟或朗讀「這是什麼」說明的人數 ÷ 到達擲筊選擇畫面人數 |
| 反覆重擲率 | 在停止提示後仍嘗試再次擲筊的人數 ÷ 已啟動擲筊人數 |
| 安全紅旗 | 任何表示筊象會取代或延後醫療、安全、法律或財務必要行動的個案數 |

## 決策門檻

核心流程可繼續進入步驟 5，需同時符合：

- A 版願望保存完成率至少 80%。
- 真實宮廟代辦誤解率低於 10%。
- 至少 50% 目標使用者有具體真實情境試用意願。
- 顧問沒有未處理的重大文化風險。

B 版只有在以下條件全部成立時，才能進入步驟 5 的 UX／GUI 審查：

- B 版願望保存完成率不低於 A 版；若小樣本只差 1 人，記為不確定並擴充樣本或改版重測，不直接判定通過。
- 超過半數 B 版受測者能在未提示下同時說明「願望已完成」與「結果只是數位文化體驗」。
- 停止提示後的再次重擲率低於 10%。
- 權威／決策指令誤解率低於 5%。
- 安全紅旗為 0。
- 顧問已核可或有條件核可筊象名稱、結果說明、數位揭露與停止規則。

未達 B 版門檻不影響 A 版核心祈願繼續開發。不得用偏好分數或「覺得有趣」取代理解與安全門檻。

## 研究資料管理

- 招募聯絡資料若確有需要，放在專案外且與 `participant_id` 對照表分開；本 repository 不保存。
- 錄音、錄影或螢幕錄製必須逐次取得同意；拒絕錄製不影響參與。
- 計分表只記行為、勾選與去識別化摘要，不逐字抄錄敏感人生處境。
- 未另行取得同意時，原始影音在研究結論確認後 30 天刪除；去識別化計分與決策紀錄可留作產品稽核。
- 報告不得用 AI 模擬受訪者、顧問或虛構數據補足樣本。
