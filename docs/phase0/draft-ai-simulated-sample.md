> 依 [README](README.md) 最後一條研究資料管理規則，正式的完成率、誤解率、門檻判定、
> `session-scorecard.csv` 與 [結果與決策](結果與決策.md) 一律不得使用本檔案內容——
> 後者本身也在檔案開頭寫明「不得用推測、AI 模擬或虛構數據填寫」。
>
> 本次已依 README 的樣本規模全量模擬：
>
> - 探索訪談 **18 / 15–20**（三層經驗各 6 人，達每層至少 3 人的配額）
> - 原型測試 **10 / 8–10**（從 18 位探索訪談者中挑出，AB／BA 各半）
> - 顧問審閱 **4 / 3–5**
> - 7–14 天回訪 **10 / 10**（僅原型測試參與者）
>
> 對應的模擬計分列在 [draft-ai-simulated-sample-scorecard.csv](draft-ai-simulated-sample-scorecard.csv)；

## 原型測試詳述（10 人，AB／BA 各半）

以下依觀察重點分「重點案例」與「一般案例」，重點案例刻意涵蓋 README 特別要求不能被平均分數稀釋的情況（安全紅旗、代辦誤解、停止後重擲、理解不穩定），一般案例示範乾淨通過的樣子。完整逐列數值見 CSV。

### 重點案例

**P002（sometimes，BA，研究情境二→一）**——理解不穩定的臨界案例。B 版一開始沒發現可以略過擲筊，摸索後才找到；擲出「聖筊」後說「這樣是不是代表一定會成功」，追問筊象性質時先答「代表神明同意」，被反問才改口「應該只是遊戲設定」。未主動點開說明（`disclosure_opened = no`）。用來測試主持人是否會把「先答錯、被追問才改口」正確記為未達「未提示下能說明」的門檻，而不是寬鬆地算通過。

**P004（frequent，BA，研究情境二→一）**——真實宮廟代辦誤解案例。兩版結束後都表示「感覺像是某間真實宮廟推出的線上版」，即使主持人重複品牌介紹卡（「完全虛構、不代辦」）後仍未改口。用來測試「真實宮廟代辦誤解率」欄位是否會被漏記——這類回答不能因為受測者其他分數高就被平均掉。

**P006（rare，BA，放大字體使用者）**——安全紅旗＋需要協助案例。B 版被問「如果涉及緊急狀況，結果會不會讓你延後求助」，回答「會想先看結果穩不穩，再決定要不要找人幫忙」，記為 `high_stakes_safety_signal = yes`。A 版因放大字體下保存按鈕與背景對比不足，找了很久，主持人依規則直接告知下一步才完成（`needed_help = yes`）。這一列示範：安全紅旗只要出現一次就整體記為 `yes`，不能被同一人其他正向回答稀釋，也是 README 明訂的規則。

**P007（frequent，AB，iPad）**——需要協助但最終完成案例。A 版一開始沒注意到保存按鈕在畫面下方（iPad 版面捲動範圍較大），主持人提示「往下滑看看」後才完成，`needed_help = yes`、耗時 45 秒。B 版反而操作更順暢。用來測試「願望保存完成率」計算時，`needed_help = yes` 仍計入完成（`wish_saved = yes`），但需要另外揭露「需要協助的比例」，不能只看完成率就當作體驗沒問題。

**P008（sometimes，BA）**——停止後仍重擲案例。B 版擲出「聖筊」後，看到停止提示仍再擲一次，理由是「想確認是不是聖筊才是真正答案」。用來測試「停止後再次重擲率」欄位是否會被正確記錄，這類個案在小樣本下很容易讓整體比率跨過 10% 門檻（實際彙整結果見決策草稿）。

### 一般案例（乾淨通過）

- **P001（frequent，AB）**：兩版皆流暢完成，B 版主動讀說明、重擲一次後依提示停止，理解正確。
- **P003（rare，AB，iPad）**：新手但耐心讀完說明才擲筊，未提示下能同時說明「願望已完成」與「這只是文化體驗」，零重擲。
- **P005（sometimes，AB）**：兩版操作正常，理解正確，無重擲。
- **P009（rare，AB）**：第一次接觸擲筊規則，仍順利完成兩版，給分偏高。
- **P010（frequent，BA）**：兩版中完成速度最快的一組，理解正確。
