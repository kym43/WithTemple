> 狀態：Phase 0 已於 2026-09-30 改採 Agent-only 快速驗證並完成；不含擲筊的核心祈願流程可直接進入 UX／GUI 審查與 Phase 2A。此決策解除真人招募、顧問訪談及 7–14 天回訪對核心開發的阻擋，但不宣稱已完成市場或文化實證。擲筊只保留內部原型，不納入公開 MVP。Xcode 專案已建立（Phase 1 骨架），iPad device family／方向設定已完成；自適應版面仍須在 Phase 2 實作及進行實機／多工驗收。

## 1. 產品願景

打造一款以台灣民俗信仰文化為基礎的私人數位祈願與文化體驗 iOS app，讓使用者能在手機上進行引導式參拜、許願紀錄，並認識廟宇文化與神明由來；若使用者不想進行線上參訪，也可搜尋附近的實體廟宇並開啟地圖前往。產品結構維持「私人祈願核心＋民俗文化支線＋每日輕量文化入口」，不發展成泛算命或命令使用者做決策的工具箱。**本產品為完全虛構的「線上廟宇」品牌，不代表任何實體宮廟，不代辦實體宗教儀式，也不保證任何祈福、筊象、籤意或宜忌結果；附近廟宇搜尋結果也不代表本產品與該廟宇具有合作、認證或代辦關係**（見第 7 節第 2、10–12 項）。「安太歲」「點光明燈」等功能名稱沿用民俗慣用語，但實質是使用者的個人數位祈福紀錄，不等同真實宮廟的正式登記。擲筊、求籤與今日宜忌若通過驗證後上線，皆定位為清楚揭露來源與限制的數位文化體驗／自我反思參考，不預測未來，也不取代醫療、法律、財務、安全或其他專業判斷。目標是用現代化、視覺化且尊重文化的方式，提供低壓力的私人祈願體驗，同時尊重使用者選擇親自前往實體廟宇的需求。

### 目標受眾（待確認，先列假設）
- 無法常常回廟裡拜拜的信眾（離鄉遊子、忙碌上班族）
- 對民俗信仰文化有興趣、想了解神明由來的年輕族群
- 想幫家人安太歲/點燈但不方便親自到廟的人
- 不認同或不習慣線上參拜、希望尋找附近實體廟宇親自前往的人

## 2. 核心功能

| # | 功能 | 說明 |
|---|------|------|
| 1 | 拜拜 / 許願 | 線上參拜流程（選神明 → 可略過的拈香／獻供文化引導 → 以文字寫下或在心中默念願望），純屬個人私密紀錄；MVP 不蒐集原始語音 |
| 2 | 安太歲（個人數位祈福紀錄） | 依生肖／儀式年度免費建立個人數位安太歲紀錄，僅使用者自己可見，非真實宮廟正式登記；完成後可自願選擇 1／2／3／4 USD 支持開發，略過或未付款不影響紀錄 |
| 3 | 點光明燈（個人數位祈福紀錄） | 選燈位樣式、填寫祈福對象並免費建立當年度個人數位紀錄，僅使用者自己可見，非真實宮廟正式登記；完成後可自願選擇 1／2／3／4 USD 支持開發，略過或未付款不影響紀錄 |
| 4 | 廟宇介紹 | 廟宇沿革、建築特色、參拜須知 |
| 5 | 神明介紹 | 玉皇大帝、月老、媽祖、關公等神明的由來、常見祈求、信仰脈絡、各地差異與參拜提醒，並標示來源及審閱資訊 |
| 6 | 廟宇視覺入口 | 廟宇外觀圖，點擊後進入內部場景瀏覽擺設（3D，見第 5 節） |
| 7 | 台灣廟宇建築百科 | 介紹台灣傳統廟宇的建築組成與工法，例如三川殿、龍柱、石獅、屋頂形式（燕尾脊/馬背）、剪黏、交趾陶、藻井、木雕/石雕、門神、匾額對聯等；可搭配 3D 內部場景做互動熱點導覽 |
| 8 | 個人祈願牌 | 將願望視覺化為個人的「祈願牌／祈願卡」，放在首頁祈願場景或個人祈願牆；僅使用者自己可見，不做公開社群牆，也不宣稱是台灣宮廟的統一正式習俗 |
| 9 | 文化探索機制 | 隨使用者完成文化閱讀、免費參拜與定期回顧願望，逐步開放新的文化故事、建築導覽或節慶展區；**不與付費金額掛鉤，不以神明、靈驗度或廟宇大小作為遊戲獎勵**（細節待驗證，見第 7 節第 8 項） |
| 10 | 附近實體廟宇 | 使用者不想線上參訪時，可在主動操作後使用目前位置搜尋附近廟宇，依約略直線距離排序，查看名稱、距離與地址，並在 Apple 地圖中開啟地點或規劃路線；搜尋結果來自第三方地圖資料，不代表合作、認證或資訊完整正確（見第 7 節第 10 項） |
| 11 | 擲筊請示（內部原型，非公開 MVP） | 願望已完成並保存後的可選數位文化體驗草案；本期僅置於 feature flag／開發版，不接正式導覽、持久化、付費或商店素材。日後若要公開，才啟動真人使用者測試與民俗／宮廟顧問審閱；不是願望成立條件，也不宣稱結果是神明真實回覆 |
| 12 | 求籤／籤意導讀 | 獨立的問事文化流程，採單一、有來源及版本、經顧問審閱的籤系，呈現原文、白話意涵、文化典故與反思問題；不提供確定性預言或 AI 即時個人化解籤 |
| 13 | 今日宜忌（民俗參考） | 首頁次要的每日文化卡；標示國曆、農曆、時區、資料來源／版本及「不同版本可能不同」，不根據生日、生肖或地址自行產生個人化命令 |

## 3. 資訊架構（導覽結構草案）

採用 Tab 導覽，四個主要分頁：

```
TabView
├── 首頁（廟宇）  ── 2D 廟宇視覺入口 + 個人祈願牌場景、公告、快捷儀式按鈕；點擊廟宇進入內部/3D 場景；另設「想親自參拜？尋找附近廟宇」次要入口；今日宜忌卡不進公開 MVP
├── 儀式          ── 許願 / 安太歲 / 點光明燈；擲筊、求籤與籤意導讀不進公開 MVP 導覽
├── 神明百科      ── 神明列表 → 神明詳情（由來、常見祈求、信仰脈絡、參拜提醒）；另設建築、籤詩與農民曆文化說明
└── 我的          ── 個人願望／祈福紀錄、通知設定、資料管理、關於廟宇；筊象／籤意紀錄不進公開 MVP
```

「個人祈願牌」傾向規劃為首頁場景中的互動節點，而非獨立分頁；使用者在此瀏覽／管理自己的祈願牌（僅個人可見，【產品假設】，見第 7 節第 5 項）。日本繪馬、首爾戀愛鎖等案例只保留為內部產品靈感，不直接套用為台灣廟宇的視覺或文化宣稱。

擲筊內部原型仍以許願完成後的可選步驟設計；求籤／籤意導讀是未來獨立的較深支線；今日宜忌只負責未來的每日輕量入口。三者目前都不進公開 MVP 導覽、不新增 Tab，也不在首頁平鋪為同等權重的小工具，避免稀釋「心願廟」的私人祈願核心。

「附近實體廟宇」不新增第五個 Tab，以免與 App 的私人數位祈願主流程競爭；從首頁次要入口進入獨立搜尋頁，預設以距離排序的清單呈現並可切換地圖。只有在使用者點擊「使用目前位置」時才要求定位權限；若拒絕、受限制或關閉定位，仍可手動輸入地區搜尋。

## 4. 資料模型草案

```
Temple            廟宇基本資料（名稱、簡介、沿革、特色、圖片）——虛構廟宇，不設真實地址
Deity             神明（名稱、別名、由來故事、職掌、祭拜方式、圖片/3D位置錨點）
ArchitectureFeature 廟宇建築元素（名稱、類別如樑柱/屋頂/雕飾、說明文字、圖片、3D位置錨點），例如龍柱、燕尾脊、剪黏、藻井
RitualType        儀式種類 enum（拜拜 / 安太歲 / 點光明燈 / 許願 / 擲筊 / 求籤）
WishEntry         許願紀錄（使用者、對象神明、內容、時間）——預設且永久為私人，不提供公開選項
JiaobeiRecord     未來公開擲筊才評估的獨立紀錄（關聯願望、筊象、擲筊時間、流程／文案版本）——不屬於 SwiftData V1 或內部原型交付；不得保存使用者心中默念的問題
FortuneSet        籤系內容版本（名稱、來源／授權、版本、適用脈絡、編輯／顧問、審閱日期）——一個版本內不得混搭不同來源籤系
FortuneSlip       籤詩（所屬籤系、籤號、原文、白話意涵、文化典故、反思問題、風險提示）
FortuneDrawRecord 求籤紀錄（籤系版本、籤號、抽取時間、是否保存）——不預設保存使用者所問文字
AlmanacDay        每日民俗參考（國曆日、農曆顯示、時區、宜／忌摘要、說明、來源／編算版本、修訂日期）
AnnualRitualCycle 儀式年度設定（穩定識別碼、顯示名稱如「2027 丁未年」、開始／結束日期、是否開放）——日期由每年度內容設定提供，不以固定國曆日期寫死
LightLampRecord   光明燈個人數位紀錄（燈位樣式、祈福對象暱稱、儀式年度、建立時間、狀態）——不收生日等真實個資，與支持交易分離
TaisuiRecord      安太歲個人數位紀錄（生肖、儀式年度、暱稱、建立時間、狀態）——與支持交易分離
RitualSupportTier 自願支持固定級距（StoreKit 商品 ID、美國基準價格 1／2／3／4 USD）——四個通用支持商品供兩種年度儀式共用，實際顯示價格由 StoreKit 回傳；原生銷售報表只能依商品 ID 彙總，不能據此區分儀式來源
SupportTransaction 自願支持交易（儀式類型、儀式年度、商品 ID、交易 ID、購買日期、環境、退款／撤銷狀態與日期）——用交易 ID 防止同筆付款重複處理，不作為祈福紀錄完成條件
UserProfile       使用者基本資料（可選暱稱、祈福紀錄關聯）——不收真實姓名
NearbyTempleResult 附近實體廟宇的暫時性搜尋結果（名稱、座標、地址、距離、地圖項目）——與虛構 Temple 分開，不寫入持久化資料庫
```

延續 MVVM 慣例：Model 純資料、Service 負責存取（先用本地 Mock / 之後可接雲端）、ViewModel（`@MainActor`）負責畫面狀態與流程邏輯、View 只做呈現與導覽。

## 5. 技術架構

- **UI**：SwiftUI，MVVM
- **裝置範圍**：MVP 支援 iPhone 與 iPad，最低系統版本同為 iOS／iPadOS 18.0。`project.yml` 的 `TARGETED_DEVICE_FAMILY` 已設為 `"1,2"`；iPhone 維持直向，iPad 已開放直向、倒置直向與兩種橫向，且未設定 `UIRequiresFullScreen`，保留可調整大小的多工視窗能力。這項設定屬 Phase 1 工程基線，用來提早暴露兩種裝置的編譯、方向與資產問題，不等同 iPad 介面已驗收，也不會單憑本機設定直接公開 App Store 可用性。Phase 2 須先完成 UX／GUI 審查，再實作 iPad 自適應版面並進行實機／模擬器與多工視窗測試；App Store 素材則在送審前依已驗收畫面製作。iPad 不只放大 iPhone 畫面：regular width 可評估自適應側邊欄／雙欄內容，窄視窗回到堆疊式導覽。Apple Silicon Mac 相容模式不列入 MVP 承諾，須另行驗證後才在 App Store Connect 開放
- **首頁廟宇視覺**：2D 呈現（插畫／圖片素材），包含廟宇外觀與個人祈願牌場景，一般 SwiftUI 排版即可完成，不需要 3D 引擎（【技術暫定】，見第 7 節第 7 項）
- **廟宇內部場景**：點擊廟宇後才進入，使用 RealityKit（依你先前選擇），以 `RealityView` 呈現可環顧的廟宇內部；MVP 階段先用簡化幾何/佔位素材，之後再換上正式 3D 模型與美術資源
  - 內部場景可放置 `ArchitectureFeature` 對應的互動熱點（例如點擊龍柱、屋頂彈出說明卡片），把「台灣廟宇建築百科」內容與 3D 導覽自然結合，規劃在 Phase 4（見第 6 節）
- **服務層**：protocol-backed services，例如：
  - `TempleContentServicing`（廟宇/神明內容）
  - `WishServicing`（許願紀錄存取）
  - `RitualServicing`（安太歲/點燈登記）
  - `NearbyTempleSearching`（附近實體廟宇搜尋，封裝 MapKit/Core Location）
  - `DivinationContentServicing`（經審閱的擲筊說明、籤系與籤意內容；保留來源與版本）
  - `AlmanacServicing`（每日宜忌資料、來源版本、時區與更新／勘誤狀態）
  - 皆搭配 `Mock*` 版本供開發與測試使用
- **文化內容更新**：Phase 2 與封閉原型先使用隨 App 版本發布的唯讀、版本化 JSON 內容，確保離線可用、內容與 App 行為可一起審查；此階段的勘誤須跟隨 App Store 版本更新，介面不得承諾即時修正。完整求籤／農民曆若通過 Phase 4 上線門檻，再加入自有網域的第一方靜態 HTTPS 內容端點／CDN：只下載不含可執行程式碼的簽章版本清單與內容檔，不傳願望、求問、位置、裝置識別碼、Cookie 或個人化參數；下載後驗證版本、適用日期、數位簽章與 checksum，採原子更新並保留 last-known-good 及 App 內建 fallback。內容端點不可兼作行為追蹤或遠端操控付費／筊象／籤詩結果；若團隊無法承擔全年更新、勘誤與端點維運，就維持 App 版本夾帶內容而不推出完整農民曆
- **持久化**：MVP 先用本地儲存（SwiftData 保存紀錄，UserDefaults 只放設定），資料模型需保留帳號擴充性；之後若要雲端同步紀錄/跨裝置同步，可平滑升級為後端服務（【技術暫定】暫不做帳號系統，見第 7 節第 4 項）。目前 `WishEntry`／SwiftData V1 只保存願望；若擲筊／求籤通過驗證並需要持久化，沿用現有 `VersionedSchema` 與 `SchemaMigrationPlan` 建立 V2，使用獨立紀錄模型，不把新欄位全部塞進 `WishEntry`。現有 migration plan 已有骨架且 `stages` 尚空，技術路徑清楚，但仍需為實際 schema 變更補 migration 與重開／匯出測試
- **Privacy Manifest 與 API 盤點**：已建立 App target 的 `PrivacyInfo.xcprivacy`、盤點文件與靜態檢查腳本。依 Apple 的 [Required Reason API 說明](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)，App 或所含第三方 SDK 實際使用清單內 API 時，必須在各自 bundle 的 privacy manifest 宣告核准理由。目前 App source 並未使用這些 API，因此不預先宣告理由；規劃中的 app-only `UserDefaults` 若實作，須依當時官方清單使用與實際用途相符的理由（現行常見為 `CA92.1`）。不能因使用 SwiftData、產生 JSON `Data` 或一般檔案操作就一概推定需要 file timestamp 理由；只有直接使用 `creationDate`、`contentModificationDateKey`、`stat` 等官方列出的檔案時間戳 API 時才申報相應類別。每次 Archive 產生 Xcode Privacy Report，核對 App Store 隱私標籤、manifest、實際程式與第三方 SDK 清單一致，不多報也不漏報
- **分析、日誌與當機診斷**：MVP 僅採 Apple 原生能力，不導入第三方分析、廣告或當機回報 SDK。操作日誌使用 `Logger`／OSLog，優先只記固定事件與非敏感錯誤碼；任何動態值預設標記 `.private`／`.sensitive`，且願望、求問、暱稱、位置、籤意與筊象不得寫入日誌。當機與效能先使用使用者同意分享的 Xcode Organizer／App Store Connect 診斷；MetricKit 只用於開發／測試或裝置內診斷，MVP 不把 payload 上傳自有或第三方伺服器。第 8 節的自訂事件名稱目前是研究量測規格，不代表已導入遠端事件蒐集；若上線後確實需要功能級分析，另立決策評估第一方最小化計數或經審核供應商、保存期限、隱私標籤、Privacy Manifest／SDK 簽章及退出方式
- **金流**：拜拜、許願、安太歲與點光明燈個人數位紀錄全部免費完成；安太歲或點光明燈完成後，可自願透過 StoreKit 消耗型 In-App Purchase 支持開發團隊，四個共用固定級距的美國 storefront 基準價格暫定為 1／2／3／4 USD，不提供自由輸入金額。略過、取消、待處理、失敗或退款均不影響祈福紀錄；所有支持級距也不改變紀錄內容、視覺、燈位、祝福文案、祝福效果或文化探索進度。App 內一律顯示 StoreKit 回傳的當地幣別與價格，不硬編碼 USD（【產品假設＋技術暫定】，見第 7 節第 3 項）
- **本地化**：繁體中文 + 英文兩語系架構（【技術暫定】，見第 7 節第 6 項），採字串檔案管理；MVP 內容先以繁體中文為主，其餘語系與完整英文內容日後視驗證結果擴充。籤詩的原文、白話意涵、典故、反思問題，以及全年農民曆資料均是高成本內容本地化，不得只把介面字串已雙語化就視為功能已支援英文
- **附近實體廟宇**：使用 Core Location 取得一次性的前景位置，以 MapKit `MKLocalSearch` 在指定區域分別執行「廟宇／宮廟／寺廟／道觀」等可本地化、可經實測調整的自然語言查詢，合併並依地圖項目識別資訊、名稱與座標去重後，再依使用者位置計算約略直線距離排序。原生 MapKit 沒有可單獨涵蓋台灣廟宇的公開 POI 類別，因此名稱關鍵字與地圖分類只用於保守的相關性加權，不以是否包含「廟、宮、壇、寺」等單一字詞硬性排除結果；Phase 2C 須以都市、偏鄉及離島樣本驗證前 10／20 筆結果的正確率。搜尋範圍【技術暫定】先採 5 公里，少於 5 筆時依序擴至 15、30 公里，合併去重後最多顯示 20 筆；使用 `regionPriority = .required` 約束 MapKit 回傳區域，並再次以直線距離排除範圍外結果。手動地區搜尋使用 `MKLocalSearchCompleter` 提供鄉鎮市區或地標建議；使用者選取建議後，以 `MKLocalSearch.Request(completion:)` 取得 `MKMapItem` 的座標與區域，作為相同 5／15／30 公里搜尋及排序的中心。自由文字直接搜尋可由 `naturalLanguageQuery` 處理，但正式流程以選取建議為主，降低同名地區、錯字及模糊地名造成的歧義；新實作不採用已被 Apple 標示 deprecated 的 `CLGeocoder.geocodeAddressString`。點擊結果透過 `MKMapItem.openInMaps` 在 Apple 地圖中開啟地點或規劃路線，路線計算、預估時間與導航均由 Apple 地圖提供，WishTemple 不自行提供導航。只申請「使用 App 期間」權限，不使用背景定位、不持續追蹤，也不把位置、查詢或結果寫入本地紀錄、分析事件、日誌或自有伺服器；應支援降低精確度的位置及手動地區搜尋 fallback

## 7. 待確認事項與目前決議

以新創公司內部討論的方式，先針對以下事項推演出目前傾向方向。**Phase 0 Agent 快速驗證已完成，但仍不是使用者或文化顧問實證**，因此必須區分「可進開發」與「已由真人驗證」，避免把開發決策誤寫成市場或文化定案：

- 【Agent 案頭通過】：公開來源、內部一致性與風險護欄足以支持限縮範圍開發，但不代表市場或文化實證

- 【真人驗證完成】：已透過實際訪談、行為測試或顧問審閱驗證（目前尚無任何項目達到此狀態）

   - MVP 階段不需要登入帳號，使用者拜拜/許願時默念在心裡即可（與實體拜拜體驗一致），資料先以裝置本地儲存（SwiftData，設定另存 UserDefaults）。
   - 架構上保留帳號擴充性：Model 與 Service 層以 protocol 抽象設計，之後要加 Apple 登入 + 雲端同步時可平滑升級，不需重寫資料層。
   - 安太歲／點光明燈紀錄同樣先存在本機；由於紀錄本身免費，刪除 App、換機未移轉或裝置損壞造成的資料遺失不涉及付費功能遭撤銷，但購買前後仍須清楚說明本機資料限制，並提供資料匯出。是否採用 SwiftData + CloudKit 私人資料庫同步，須和願望內容上雲的隱私取捨一併驗證，不因加入自願支持而自動啟用。

5. **許願牆／社群功能** — 【產品假設（縮小範圍為個人版）】
   - 目前只做「個人許願牆」，不做公開社群留言板，避免一開始就要做內容審核機制；願望紀錄永久預設私人，不提供公開選項（見第 4 節 WishEntry 模型）。
   - 視覺呈現改以中性的個人「祈願牌／祈願卡」為主。日本神社繪馬牌、首爾塔戀愛鎖等僅是內部互動案例參考，不直接移植為台灣廟宇習俗，也不在對外文案暗示文化等同。
   - 未來若要做公開/社群版本，可當作獨立的 Phase 5+ 功能再評估（屆時需一併設計審核機制）。

6. **多語系範圍** — 【技術暫定】
   - 先保留繁體中文、英文兩語系的本地化架構（字串檔案管理），但 MVP 內容以繁體中文為主；待驗證海外客群需求後，再投入完整英文內容製作，避免過早投入未經驗證的翻譯成本。
   - 求籤上線所需的籤詩原文處理、白話意涵、典故、反思問題與風險提示都須逐篇翻譯、文化調整與複核；農民曆若做全年內容，還包含每日宜忌與來源說明的持續在地化。Roadmap 須另估內容編輯、翻譯、顧問審閱與年度更新工時，不能只估 UI／工程字串。

7. **首頁呈現方式與 3D 素材** — 【技術暫定】
   - 首頁採 2D 呈現（廟宇外觀＋個人祈願牌場景），點擊廟宇後才進入內部場景／3D 視角。
   - 個人祈願牌作為首頁互動節點，可用經顧問審閱且不冒充特定正式習俗的視覺方式呈現。日本繪馬、戀愛鎖等案例僅供內部互動參考，不直接套用其文化外觀。
   - 此決定讓 MVP 初期可用一般圖片/插畫素材完成首頁；廟宇內部/建築百科導覽場景建議先用 2D 熱點驗證互動設計，待有使用數據支持後再投資 RealityKit 正式 3D 資產（RealityKit 4 的跨平台 `RealityView` 為 WWDC24 世代能力，若採用需在此明訂 deployment target 與最低裝置，並規劃 2D fallback，詳見第 5 節）。

8. **文化探索機制與遊戲化風險** — 【產品假設，Phase 5 前需重新驗證】
   - 原「簡陋小廟 → 大廟」「解鎖／請神明進駐」「許一個願，蓋一座廟」構想暫停採用。即使完全免費，這類敘事仍可能把神明物件化、把廟宇大小等同信仰等級，與是否綁定付費是兩個不同風險。
   - 若未來需要成長回饋，優先考慮隨文化閱讀、定期回顧願望、免費參拜、探索建築知識與節慶活動，逐步開放新的文化故事、建築導覽、節慶展區或個人閱讀收藏；不以神明、靈驗度、香火量、廟宇規模作獎勵，也不把信仰對象設計成稀有角色。
   - 待討論的細節：
     - 探索範圍：全站共用一份文化探索進度（需要後端服務同步），還是每個使用者各自保存閱讀／參拜進度（可維持本地儲存）？這會直接影響第 4 節帳號系統與第 5 節持久化的技術選型，需先決定再設計。
     - 探索門檻與階段數：每級對應多少文化探索進度，如何避免為了數字反覆操作儀式？
     - 美術與內容資源：每個文化展區需要哪些 2D 場景、導覽內容與顧問審閱？3D 是否同步擴充留待後續評估。
     - 回饋敘事：如何讓使用者感到累積與陪伴，又不把神明、筊象、籤詩或信仰虔誠度當成獎勵？
   - 建議：先列為 Phase 5 的加值功能，MVP 使用固定廟宇場景，不預先製作廟宇升級美術，也不建立神明解鎖故事線。
   - 付費與進度界線：所有探索進度來源都必須有免費取得方式；安太歲／點光明燈的年度免費完成行為可依未來統一規則計算文化探索進度，但自願支持是否購買、購買次數及 1／2／3／4 USD 級距一律不產生或增加進度。同一儀式年度的重複紀錄不得被用來付費加速探索。

9. **個資原則** — 【產品假設，尚待法務確認台灣個資法適用範圍】
   - 不收真實姓名，改用可選暱稱或稱謂；不收完整生日，生肖由使用者自行確認；先移除原始語音蒐集。
   - 願望紀錄永久預設私人；求問內容不要求輸入且預設不儲存。若未來允許保存，必須比照願望提供逐筆刪除、全部刪除與匯出。分析、日誌及崩潰報告不得包含暱稱、願望、求問內容或可推測宗教與人生處境的敏感文字。
   - `featureEntered`、`ritualCompleted`、`resultViewed`、`reflectionSaved` 等目前只是研究量測名稱。MVP 不導入第三方分析／當機 SDK，也不把這些事件遠端送出；先以受控訪談／測試記錄、App Store Connect 的彙總指標及 Apple 原生診斷建立基線。若日後需要第一方或第三方事件分析，須先另行確認資料欄位、必要性、保存期限、退出方式、App Store 隱私標籤、Privacy Manifest 與 SDK 簽章。籤號與筊象可能與使用者處境形成敏感推論，未完成評估前不蒐集。
   - 提供逐筆刪除、全部刪除功能及資料遺失說明；App Store 上架需提供隱私政策網址並如實申報資料處理方式。
   - 位置權限、手動地區搜尋及 MapKit／Apple 地圖服務的資料處理另依本節第 10 項規範；隱私政策與 App Store 隱私申報檢查清單必須一併涵蓋該項，不得因位置不寫入本地資料庫就略過審查。

10. **附近實體廟宇** — 【產品假設＋技術暫定，待使用者測試與實機驗證】
   - 產品目的：提供不想、不習慣或不認同線上參訪的使用者一條清楚的實體參拜路徑，而不是把所有人留在虛構線上廟宇中。
   - 入口與流程：首頁以次要卡片顯示「想親自參拜？尋找附近廟宇」；進入說明頁後，由使用者主動點擊才請求定位。成功後顯示依約略直線距離排序的清單，可切換地圖；點選廟宇後顯示名稱、地址、約略距離及「在 Apple 地圖中開啟／規劃路線」。WishTemple 本身不提供路線計算或導航。
   - 權限與替代流程：只要求「使用 App 期間」的位置權限，不要求「永遠允許」或背景定位；拒絕權限、定位受限制、降低精確度、無法取得位置時，仍提供手動輸入鄉鎮市區或地標的搜尋方式。未操作附近搜尋前不在 App 啟動時要求權限；手動搜尋改以所選地區中心作為排序基準，不把該距離標示為「距離你」，避免讓使用者誤以為 App 仍取得其位置。
   - 資料與隱私：位置只用於當次搜尋與距離計算，不建立足跡、不保存最近搜尋、不寫入分析或崩潰日誌，也不傳至自有後端；正式實作與上架前仍須說明 MapKit／Apple 地圖服務的資料處理方式，並在 `NSLocationWhenInUseUsageDescription` 清楚解釋用途。本項須與第 9 項個資原則一併納入隱私政策、App Store 隱私申報及第三方 SDK 資料盤點。
   - 搜尋與篩選策略：原生 MapKit 沒有能單獨涵蓋台灣廟宇的公開 POI 類別；先以「廟宇／宮廟／寺廟／道觀」等多組在地化自然語言查詢取得候選結果，再合併去重並作保守的相關性排序。名稱是否包含「廟、宮、壇、寺」等字詞只作加權參考，不作硬性納入或排除條件；正式查詢詞與排序規則須以不同地區實機結果調整。
   - 搜尋範圍與數量：【技術暫定】先搜尋 5 公里；少於 5 筆時自動擴至 15 公里，再不足時擴至 30 公里，每次顯示目前範圍並允許使用者主動擴大。合併去重後最多顯示距離最近的 20 筆，避免都市結果過多，同時降低偏鄉完全無結果的機率。
   - 資料可信度：結果為地圖搜尋服務提供，可能有遺漏、分類錯誤、地址或開放資訊過期；App 不建立「官方廟宇名冊」，不顯示自行推定的祭祀服務、營業時間或宗派，也不宣稱推薦、認證或合作。介面應提示使用者出發前以廟宇官方資訊確認。
   - 搜尋定義：使用目前位置時，「最近」指目前搜尋範圍內由地圖服務回傳且通過基本相關性排序的候選結果，再依使用者位置計算約略直線距離排序；手動地區搜尋則依所選地區中心排序。兩者都不保證涵蓋所有實體廟宇，也不等同實際步行或行車距離。地點顯示、路線、時間與交通方式交由 Apple 地圖處理。
   - UX 狀態：至少涵蓋首次說明、定位詢問、載入、成功、無結果、網路失敗、定位失敗、權限遭拒／受限制及重新搜尋；權限遭拒時提供前往系統設定與手動搜尋，但不得反覆強迫要求權限。
   - GUI／無障礙：結果頁以清單為主要呈現、地圖為可選模式；卡片需支援 Dynamic Type、VoiceOver、深色模式與足夠觸控區域，距離不可只用地圖視覺或顏色表達。

11. **擲筊、求籤與今日宜忌的產品角色** — 【Agent 案頭通過；公開功能仍待真人驗證】
   - 三項功能不並列成泛命理工具箱，而是分別承擔「核心儀式補完／深度文化支線／每日輕量入口」：
     - 擲筊：願望已保存後的可選文化體驗；不決定願望是否成立。
     - 求籤／籤意導讀：獨立問事流程；使用者先在心中確定一件可清楚表達的事情，再依本產品採用且經顧問核定的流程體驗。不同宮廟對是否需要一個或連續多個聖筊確認籤支可能不同，介面只稱「本體驗採用的流程／常見做法之一」。
     - 今日宜忌：首頁次要文化卡；帶往文化說明、參拜或願望回顧，不成為生活行動的強制閘門。
   - 擲筊流程僅作內部原型：選擇神明 → 靜心／參拜引導 → 一次陳述一件願望 → 先保存私人願望 → 可選「擲筊請示」→ 顯示圖形、名稱與中性文化說明 → 回到紀錄。不要求輸入或儲存問題文字；公開前不得接入正式導覽或資料模型。
   - 筊象文案不得使用「願望成功／失敗」「大吉／凶兆」「神明生氣／拒絕你」。Agent 案頭研究已確認公開來源存在名詞與陰陽面稱法差異，因此內部草案不得宣稱全台統一規則；允許次數、名稱與停止提示留待未來公開驗證決定，產品指標不得鼓勵刷到聖筊。
   - 求籤結果呈現「籤詩原文／白話意涵／文化典故／可自我思考的問題／何時應尋求真人或專業協助」，使用「可以思考」「或許可留意」等非命令語氣，不使用「一定會」「不可做」「神明指示你」。第一版不做 AI 自由解籤，不針對醫療、法律、投資、懷孕、生死、犯罪、人身安全或重大感情決策提供個人化判斷。
   - 不設無限重擲／重抽、幸運值、連勝、稀有籤、每日運勢 streak、厄運倒數、排行榜或分享炫耀；首次使用與結果頁都要固定揭露「民俗文化體驗，不預測未來、不保證結果、不代替專業判斷」。

12. **App Store 審查與年齡分級** — 【技術／營運暫定，送審前須依最新版規範重查】
   - 截至 2026-09-15，[Apple App Review Guidelines 4.3(b)](https://developer.apple.com/app-store/review/guidelines/) 明列 fortune telling 屬於 App Store 已相當成熟的類別；若新 App 與市面產品沒有明顯差異或更好的體驗，可能因 Spam／同質化被拒。主要因應不是隱藏求籤功能，而是讓產品、商店文案與 Review Notes 一致呈現 WishTemple 的差異：私人願望生命週期、台灣民俗文化脈絡、來源／顧問治理、附近實體廟宇替代路徑、資料最小化與反權威護欄，而不是單一隨機抽籤工具。
   - Claude Code 提出的「可能觸發額外年齡分級」只可視為待核對風險，不能直接視為既定結果。[App Store Connect 年齡分級](https://developer.apple.com/help/app-store-connect/manage-app-information/set-an-app-age-rating)要求所有 App 依實際內容回答問卷，問卷包含 contests、simulated gambling 等機會型活動；但 Apple 官方沒有表示所有擲筊／求籤內容都自動等同 simulated gambling。正式送審時應依當時問卷、實際功能頻率、是否涉及投注／獎品等事實誠實填答，保留截圖與判斷紀錄，必要時主動提高分級，不預先承諾特定級別。
   - 求籤／擲筊不涉及投注、現金、可兌換獎品、付費改變機率或看廣告換結果；商店截圖、關鍵字與描述不得宣稱保證靈驗、預測未來或提供重大決策答案。Review Notes 應提供完整操作路徑、數位模擬揭露、重試上限、付費隔離、內容來源／權利與隱私處理方式，方便審查人員理解。
   - 上架前依 [App Store Connect 內容權利要求](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information) 確認所有第三方籤詩、農民曆資料、圖片、音效、字體與翻譯均有必要權利；每次送審前重新檢查 4.3、年齡分級、隱私申報與 StoreKit 規範，不以本版企劃記錄取代最新官方要求。
   - 上架封存檔須包含與實際 API 使用一致的 `PrivacyInfo.xcprivacy`，並用 Xcode 產生 Privacy Report 交叉核對 App Store 隱私標籤。若未來加入 Apple [指定清單內的第三方 SDK](https://developer.apple.com/support/third-party-SDK-requirements/)，須確認該 SDK 自身附有正確 privacy manifest；以 binary dependency 加入時亦須符合簽章要求。MVP 原則是不導入第三方分析／當機 SDK，減少資料供應鏈與申報風險。

13. **裝置支援範圍** — 【技術暫定，iPad 已納入 MVP】
   - MVP 支援 iPhone 與 iPad，最低版本為 iOS／iPadOS 18.0；這是同一 iOS App target 的兩個 device family，不另建獨立 iPad App。依 [Apple App Store Connect 說明](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-platforms)，若要同時在 iPhone 與 iPad 提供 App，build 必須支援兩種裝置；`TARGETED_DEVICE_FAMILY` 已由 `"1"` 調整為 `"1,2"`。
   - iPhone MVP 可維持直向為主要體驗；iPad 須支援直向、橫向及可調整大小的多工視窗，不把全螢幕直向放大視為完成。依 [Apple Layout 指引](https://developer.apple.com/design/human-interface-guidelines/layout)，測試 full screen、二分之一、三分之一與接近最小視窗寬度，並涵蓋 compact／regular size class 的切換。
   - 導覽原則：compact width 維持 Tab＋堆疊式導覽；regular width 可採自適應 sidebar／`NavigationSplitView`，列表—詳情型頁面（神明百科、籤詩文化、願望紀錄、附近廟宇）優先使用雙欄，沉浸式參拜與擲筊維持單一主要焦點。是否採 `sidebarAdaptable` 須在 UX／GUI 審查時用原型確認，不因支援 iPad 就改變四大資訊架構。
   - iPad 驗收至少涵蓋 iPad mini 與 13 吋 iPad 的直／橫向、多工窄寬、Dynamic Type、VoiceOver、鍵盤與指標基本操作，以及地圖／RealityKit 場景的效能與記憶體。App Store 上架另準備 iPad 截圖；Apple Silicon Mac 相容模式及 Vision Pro 相容執行不在 MVP 承諾內，未完成測試前於 App Store Connect 關閉可用性。

## 8. 下一步

Phase 0 已改採 Agent-only 快速驗證，結論是先開發低風險的核心 A，將擲筊 B 隔離為內部原型。真人訪談、顧問審閱與 7–14 天回訪不再阻擋 Phase 2A；這項時程選擇不等於需求、留存或文化代表性已被證明。求籤與農民曆仍受內容來源、權利、雙語成本及 App Store 差異化審查限制，不因 Phase 0 調整而提前。iPad 已確定納入 MVP，device family 與方向設定已完成；自適應版面與實機／多工驗收仍未完成。

### 正式開發順序

以下順序以最快完成可操作的核心垂直流程、延後高成本與文化敏感功能為原則：

1. **完成 Phase 1 資料骨架（已完成，2026-09-14）**：建立 `WishEntry`、`AnnualRitualCycle`、`TaisuiRecord`、`LightLampRecord`，以及對應的 Service protocol、Mock 實作與基礎單元測試。
2. **建立 SwiftData 儲存層（已完成，2026-09-14）**：已支援願望的新增、查詢、逐筆刪除與全部刪除，並建立版本化 JSON 匯出格式；設定資料規劃使用 UserDefaults，但 App source 尚未實作。
3. **補齊 Phase 2 前置技術基線（已完成，2026-09-15）**：`TARGETED_DEVICE_FAMILY = "1,2"` 與 iPhone／iPad 方向設定已在 Phase 1 完成；已新增 App target 的 `PrivacyInfo.xcprivacy`、Required Reason API／第三方 SDK 盤點文件與靜態檢查腳本。目前 App 不追蹤、不將使用者資料傳出裝置、沒有第三方 SDK，且 App source 沒有直接使用五類 Required Reason API，因此不預先宣告任何理由；每個 Release Archive 仍須用 Xcode 產生 Privacy Report 並與 App Store Connect 隱私標籤交叉比對。iPad 自適應 UI 須依步驟 5 的審查結果於步驟 6 實作，實機／多工驗收納入步驟 8，App Store 素材則納入步驟 11 的送審準備。
4. **完成 Phase 0 Agent 快速驗證（已完成，2026-09-30）**：已完成[案頭來源查證、文件一致性、隱私／安全紅隊與範圍決策](phase0/README.md)。結論為核心 A 可開發；B 只保留內部原型。既有真人研究工具保留備用，但不在目前關鍵路徑。
5. **在 UI 實作前完成核心 A 的 UX／GUI 審查**：審查不含擲筊的核心流程，並同時覆蓋 iPhone compact、iPad regular 與多工窄寬版面；確認文案、載入／空白／錯誤／離開／刪除狀態、Dynamic Type、VoiceOver、鍵盤／指標與深色模式。
6. **實作 Phase 2A 核心垂直流程與自適應 UI**：依步驟 5 通過的設計，完成選擇神明 → 參拜引導 → 填寫或默念願望 → 儲存在本機 → 從「我的」查看或刪除紀錄；同時實作 iPhone compact、iPad regular 與多工窄寬版面。完成後直接產出可操作 Alpha，不等待訪談樣本。
7. **Phase 2B 僅作內部原型**：若不影響核心排程，可在 feature flag 下實作「願望已保存 → 可選擲筊 → 中性文化說明」的無持久化草案；不得進公開 MVP、正式導覽、商店素材或付費流程。日後決定公開時才啟用真人與顧問驗證。
8. **補齊核心測試與隱私能力**：涵蓋資料新增、刪除、重複紀錄規則、資料匯出、敏感內容不進入分析／日誌、Privacy Report 與 iPhone／iPad 測試矩陣。內部擲筊原型不得持久化；只有未來公開驗證通過後，才評估 SwiftData V2 migration 與向前／向後資料驗證。
9. **開發附近實體廟宇 MVP**：完成定位前說明、手動地區搜尋、漸進式搜尋範圍、距離排序、錯誤 fallback，以及跳轉 Apple 地圖；與擲筊成效分開評估，並依量化門檻決定是否上線。
10. **把求籤與農民曆視為內容專案**：先完成來源／授權盤點、內容樣本、繁中編輯、英文在地化估工、顧問審閱流程、App bundle／第一方內容端點方案與年度維運成本，再做 12–24 首封閉求籤原型及 30 天宜忌卡實驗；兩者不直接承諾正式上線。
11. **完成 App Store 素材與送審前自查**：以已通過驗收的公開 MVP 畫面製作 iPhone／iPad 商店截圖，排除內部擲筊原型；再依最新 4.3(b)、年齡分級、內容權利、Privacy Manifest／第三方 SDK、App Store 隱私標籤與 StoreKit 規範檢查產品及商店文案。只有未來公開隨機文化功能時，Review Notes 才需另說明隨機機制、重試上限與付費隔離。
12. **核心 Alpha 穩定後再進入商業化與高成本視覺**：Phase 3 實作安太歲／光明燈年度紀錄與 StoreKit 自願支持；正式 RealityKit 3D、完整求籤、全年農民曆與遠端內容端點仍須由各自數據、來源權利與維運能力支持後才投入。

**Phase 0 Agent 快速驗證（已完成）：**
1. 比對企劃案、A／B 原型、資料模型與隱私護欄，確認 A 版可獨立成立。
2. 搜尋政府與文化機構資料，保留來源，並標記擲筊名詞與做法差異。
3. 進行反權威、安全、隱私、付費隔離及無限重試風險走查。
4. 將 B 版隔離於內部原型，移除其對公開 MVP 與 Phase 2A 的阻擋。
5. 保留原訪談、顧問與計分工具，供 Alpha 後研究或未來公開 B 前使用。
