# 心願廟 WishTemple 企劃案（草稿 v0.2）

> 狀態：規劃已定案主要方向，Xcode 專案已建立（Phase 1 骨架）。
> 正式產品名稱：中文「心願廟」／英文「WishTemple」（【產品假設】，見第 7 節第 1 項）；原工作代號 `OnlineTemple` 僅保留為 git 倉儲/資料夾名稱。

---

## 1. 產品願景

打造一款以台灣民俗信仰文化為基礎的私人數位祈願與文化體驗 iOS app，讓使用者能在手機上進行引導式參拜、許願紀錄，並認識廟宇文化與神明由來。**本產品為完全虛構的「線上廟宇」品牌，不代表任何實體宮廟，不代辦實體宗教儀式，也不保證任何祈福效果**（見第 7 節第 2 項決議）；「安太歲」「點光明燈」等功能名稱沿用民俗慣用語，但實質是使用者的個人數位祈福紀錄，不等同真實宮廟的正式登記。目標是用現代化、視覺化且尊重文化的方式，提供低壓力的私人祈願體驗。

### 目標受眾（待確認，先列假設）
- 無法常常回廟裡拜拜的信眾（離鄉遊子、忙碌上班族）
- 對民俗信仰文化有興趣、想了解神明由來的年輕族群
- 想幫家人安太歲/點燈但不方便親自到廟的人

## 2. 核心功能

| # | 功能 | 說明 |
|---|------|------|
| 1 | 拜拜 / 許願 | 線上參拜流程（選神明 → 上香/獻供動畫 → 許願文字或語音），純屬個人私密紀錄 |
| 2 | 安太歲（個人數位祈福紀錄） | 依生肖/年份建立個人數位安太歲紀錄，僅使用者自己可見，非真實宮廟正式登記 |
| 3 | 點光明燈（個人數位祈福紀錄） | 選燈位樣式、填寫祈福對象，僅使用者自己可見，非真實宮廟正式登記 |
| 4 | 廟宇介紹 | 廟宇沿革、建築特色、參拜須知 |
| 5 | 神明介紹 | 玉皇大帝、月老、媽祖、關公等神明的由來、職掌、祭拜方式 |
| 6 | 廟宇視覺入口 | 廟宇外觀圖，點擊後進入內部場景瀏覽擺設（3D，見第 5 節） |
| 7 | 台灣廟宇建築百科 | 介紹台灣傳統廟宇的建築組成與工法，例如三川殿、龍柱、石獅、屋頂形式（燕尾脊/馬背）、剪黏、交趾陶、藻井、木雕/石雕、門神、匾額對聯等；可搭配 3D 內部場景做互動熱點導覽 |
| 8 | 許願樹 / 許願牌 | 類似日本神社繪馬、首爾塔戀愛鎖的許願牌/鎖，寫下願望後「掛上」個人許願牆或首頁大樹；僅使用者自己可見，不做公開社群牆 |
| 9 | 廟宇成長機制 | 廟宇初期規模簡陋、神明較少，隨使用者完成文化閱讀/免費參拜/定期回顧願望等「文化探索進度」累積，逐步擴建、解鎖更多神明；**不與付費金額掛鉤，避免「花越多越靈」觀感**（新想法，細節待設計，見第 7 節） |

## 3. 資訊架構（導覽結構草案）

採用 Tab 導覽，四個主要分頁：

```
TabView
├── 首頁（廟宇）  ── 2D 廟宇視覺入口 + 許願樹（可掛願望牌/戀愛鎖）、公告、快捷儀式按鈕；點擊廟宇進入內部/3D 場景
├── 儀式          ── 許願 / 安太歲 / 點光明燈 的入口與紀錄
├── 神明百科      ── 神明列表 → 神明詳情（由來、職掌、如何祭拜）；另設「建築百科」子分類介紹廟宇建築組成（龍柱、屋頂、藻井等）
└── 我的          ── 個人祈福紀錄、通知設定、關於廟宇
```

「許願樹/許願牌」傾向規劃為首頁場景中的互動節點（2D 大樹意象），而非獨立分頁；使用者在此瀏覽/管理自己掛上的願望牌（僅個人可見，【產品假設】，見第 7 節第 5 項）。

## 4. 資料模型草案

```
Temple            廟宇基本資料（名稱、簡介、沿革、特色、圖片）——虛構廟宇，不設真實地址
Deity             神明（名稱、別名、由來故事、職掌、祭拜方式、圖片/3D位置錨點）
ArchitectureFeature 廟宇建築元素（名稱、類別如樑柱/屋頂/雕飾、說明文字、圖片、3D位置錨點），例如龍柱、燕尾脊、剪黏、藻井
RitualType        儀式種類 enum（拜拜 / 安太歲 / 點光明燈 / 許願）
WishEntry         許願紀錄（使用者、對象神明、內容、時間）——預設且永久為私人，不提供公開選項
LightLampRecord   光明燈個人數位紀錄（燈位樣式、祈福對象暱稱、期間）——不收生日等真實個資
TaisuiRecord      安太歲個人數位紀錄（生肖、年份、暱稱、期間）
UserProfile       使用者基本資料（可選暱稱、祈福紀錄關聯）——不收真實姓名
```

延續 MVVM 慣例：Model 純資料、Service 負責存取（先用本地 Mock / 之後可接雲端）、ViewModel（`@MainActor`）負責畫面狀態與流程邏輯、View 只做呈現與導覽。

## 5. 技術架構

- **UI**：SwiftUI，MVVM
- **首頁廟宇視覺**：2D 呈現（插畫/圖片素材），包含廟宇外觀與許願樹意象，一般 SwiftUI 排版即可完成，不需要 3D 引擎（【技術暫定】，見第 7 節第 7 項）
- **廟宇內部場景**：點擊廟宇後才進入，使用 RealityKit（依你先前選擇），以 `RealityView` 呈現可環顧的廟宇內部；MVP 階段先用簡化幾何/佔位素材，之後再換上正式 3D 模型與美術資源
  - 內部場景可放置 `ArchitectureFeature` 對應的互動熱點（例如點擊龍柱、屋頂彈出說明卡片），把「台灣廟宇建築百科」內容與 3D 導覽自然結合，規劃在 Phase 4（見第 6 節）
- **服務層**：protocol-backed services，例如：
  - `TempleContentServicing`（廟宇/神明內容）
  - `WishServicing`（許願紀錄存取）
  - `RitualServicing`（安太歲/點燈登記）
  - 皆搭配 `Mock*` 版本供開發與測試使用
- **持久化**：MVP 先用本地儲存（SwiftData 保存紀錄，UserDefaults 只放設定），資料模型需保留帳號擴充性；之後若要雲端同步紀錄/跨裝置同步，可平滑升級為後端服務（【技術暫定】暫不做帳號系統，見第 7 節第 4 項）
- **金流**：核心儀式（拜拜/許願/安太歲/點光明燈）全部免費；如提供付費項目，僅限 3–5 個 App Store Connect 預先設定固定價格的「支持開發團隊」消耗型商品，不做自由輸入金額（StoreKit 商品需預先建立固定價格，無法對應任意金額輸入），不接外部金流，付費金額不影響祝福效果或廟宇成長進度（技術暫定，見第 7 節商業模式）
- **本地化**：繁體中文 + 英文兩語系架構（【技術暫定】，見第 7 節第 6 項），採字串檔案管理；MVP 內容先以繁體中文為主，其餘語系與完整英文內容日後視驗證結果擴充

## 7. 待確認事項與目前決議

以新創公司內部討論的方式，先針對以下事項推演出目前傾向方向。**這些推演目前僅來自單人分飾多角色的內部討論，尚未經過真實使用者訪談、民俗/宗教顧問審閱，也未做任何互動原型測試**，因此下方一律不再標示「✅ 已決議」，改用以下三種狀態標示，避免團隊誤以為已完成驗證：

- 【產品假設】：內部推演出的方向，需要真實使用者訪談或顧問審閱後才能視為定案
- 【技術暫定】：工程面的暫定做法，可依技術限制或後續需求調整，非商業/文化定案
- 【研究驗證完成】：已透過實際訪談、測試或審閱驗證（目前尚無任何項目達到此狀態）

開發前建議先完成第 8 節下一步中的驗證步驟，再將對應項目升級為「研究驗證完成」。

1. **產品/專案正式名稱** — 【產品假設】傾向：中文「心願廟」／英文「WishTemple」
   - 決策過程（PM／UX／GUI／RD／Sales／Marketing 內部討論）：
     - PM：名稱要能一眼傳達「拜拜＋許願」的核心體驗，且不綁定任何真實宮廟，避免代言/授權疑慮。
     - Marketing：曾提案「拜拜go」，直覺、口語化、本地辨識度高，但偏向工具型 App 語感，且英文「BaiBai」易被誤讀成「bye-bye」，對想強調誠心祈願的品牌調性偏輕佻；也提案「平安廟／PingAn Temple」，但「平安」與知名企業「平安保險 Ping An」撞名，Sales 認為有品牌辨識風險，予以否決。
     - UX：需要中英文都好唸、好拼、好記，「心願廟／WishTemple」兩種語言念起來直覺，不需要額外教育使用者。
     - GUI：「心願」＋「廟」給出明確視覺方向——燈籠、許願牌、廟宇剪影都能自然圍繞「wish」意象發展，也呼應許願樹/許願牌核心功能（第 2 節第 8 項）。
     - RD：確認 `com.wishtemple.*` bundle identifier 未被占用、可直接使用，`WishTemple` 作為 Xcode 專案/Target 名稱在 Swift 中也不與系統框架衝突。
     - Sales：「Wish」在 App Store 搜尋語意上與許願/祈福品類的關聯度高，且與規劃中的「廟宇成長機制」（許願→香火→蓋廟）敘事一致，行銷素材可以直接用「許一個願，蓋一座廟」當 tagline。
   - 結論：定名「心願廟 WishTemple」，決議後已建立對應的 Xcode 專案（見下方）。

2. **內容來源與真實性** — 【產品假設，尚待民俗/宗教顧問審閱】
   - 廟宇為完全虛構的「線上廟宇」品牌，不對應任何特定真實宮廟；此定位需一致反映在第 1 節產品願景、第 2 節功能命名，避免使用者誤解為真實宮廟代辦。
   - 神明由來、故事、職掌等內容，透過公開資料（維基百科、民俗文化資料等）搜尋彙整後改寫。
   - 新增內容範疇：台灣傳統廟宇建築知識（三川殿、龍柱、石獅、燕尾脊/馬背屋頂、剪黏、交趾陶、藻井、木雕/石雕、門神、匾額對聯等），同樣以公開建築/文化資料搜尋彙整後改寫，作為「台灣廟宇建築百科」內容素材（見第 2 節第 7 項）。
   - 待辦：每篇內容需記錄資料來源與授權、作者/編輯、文化顧問、最後審閱日期、地區或派別差異、圖片/音效/字體/3D 模型使用權，並建立勘誤與下架流程；彙整完成後仍需人工審核宗教用詞與建築知識描述是否正確、恰當，避免對特定信仰或文化資產造成誤解或冒犯。

3. **商業模式** — 【產品假設，待測試使用者對付費的理解與意願】
   - 拜拜／上香／安太歲／點光明燈：核心儀式全部免費，不與任何付費機制掛鉤。
   - 如提供付費項目，僅限 3–5 個固定價位的「支持開發團隊」消耗型商品（透過 StoreKit In-App Purchase 處理，需在 App Store Connect 預先建立商品與價格，不支援自由輸入金額），不稱為慈善捐款或真實廟宇香油錢，且付費金額不影響祝福效果、燈位、神明或虔誠等級。
   - 技術/合規影響：凡是 App 內「數位服務／虛擬內容」的付費，依 Apple App Review Guideline 3.1.3 一律須走 StoreKit，不能接外部金流連結（見第 5 節）；若之後想改為「純贊助/斗內」性質，需另外向 Apple 確認是否符合小費/贊助的例外規則，正式送審前以 App Store Connect 最新規範為準。
   - 因不代辦真實宮廟登記，僅需可選暱稱等象徵性資訊，個資合規範圍大幅降低（見第 7 節第 9 項個資原則）。

4. **帳號系統** — 【技術暫定】
   - MVP 階段不需要登入帳號，使用者拜拜/許願時默念在心裡即可（與實體拜拜體驗一致），資料先以裝置本地儲存（SwiftData，設定另存 UserDefaults）。
   - 架構上保留帳號擴充性：Model 與 Service 層以 protocol 抽象設計，之後要加 Apple 登入 + 雲端同步時可平滑升級，不需重寫資料層。

5. **許願牆／社群功能** — 【產品假設（縮小範圍為個人版）】
   - 目前只做「個人許願牆」，不做公開社群留言板，避免一開始就要做內容審核機制；願望紀錄永久預設私人，不提供公開選項（見第 4 節 WishEntry 模型）。
   - 視覺呈現參考日本神社繪馬牌、韓國首爾塔戀愛鎖等意象，讓每一次許願變成一個可視化的「牌子/鎖」，掛在使用者自己的許願牆或首頁大樹上。
   - 未來若要做公開/社群版本，可當作獨立的 Phase 5+ 功能再評估（屆時需一併設計審核機制）。

6. **多語系範圍** — 【技術暫定】
   - 先保留繁體中文、英文兩語系的本地化架構（字串檔案管理），但 MVP 內容以繁體中文為主；待驗證海外客群需求後，再投入完整英文內容製作，避免過早投入未經驗證的翻譯成本。

7. **首頁呈現方式與 3D 素材** — 【技術暫定】
   - 首頁採 2D 呈現（廟宇外觀 + 許願樹意象），點擊廟宇後才進入內部場景／3D 視角。
   - 首頁大樹作為「許願樹」節點，可掛願望牌或戀愛鎖造型的許願物件，與廟宇並列在 2D 首頁場景中。
   - 此決定讓 MVP 初期可用一般圖片/插畫素材完成首頁；廟宇內部/建築百科導覽場景建議先用 2D 熱點驗證互動設計，待有使用數據支持後再投資 RealityKit 正式 3D 資產（RealityKit 4 的跨平台 `RealityView` 為 WWDC24 世代能力，若採用需在此明訂 deployment target 與最低裝置，並規劃 2D fallback，詳見第 5 節）。

8. **廟宇成長機制** — 🆕 新想法，待細部設計（Phase 5，不阻塞 MVP）
   - 構想：廟宇初期規模較小、神明數量少，隨使用者完成文化閱讀、定期回顧願望、完成免費參拜、探索建築知識、參與節慶文化活動等「文化探索進度」累積，逐漸解鎖更多神明、擴建廟宇規模，帶來「大家一起把小廟蓋成大廟」的參與感。**明確不與付費金額掛鉤**，避免「花越多越靈」的觀感，也不設排行榜、限時燈位、倒數焦慮或神明稀有度機制。
   - 待討論的細節：
     - 成長基準：全站共用一座會成長的廟（需要後端服務同步），還是每個使用者各自擁有一座（可維持本地儲存）？這會直接影響第 4 節帳號系統與第 5 節持久化的技術選型，需先決定再設計。
     - 成長門檻與階段數：例如分幾個廟宇規模等級，每級對應多少文化探索進度？
     - 美術資源：至少需要對應各成長階段的 2D 首頁場景圖，建議 MVP 先規劃 3 個階段（簡陋 → 中型 → 大廟），3D 內部場景是否同步升級可留待後續評估。
     - 是否搭配「新神明解鎖」故事線（廟越蓋越大才請到某尊神明進駐），會增加內容撰寫需求。
   - 建議：先列為 Phase 5 的加值功能，MVP 以固定規模的廟宇上線，之後再疊加成長機制，避免一開始範圍拉太大。

9. **個資原則** — 【產品假設，尚待法務確認台灣個資法適用範圍】
   - 不收真實姓名，改用可選暱稱或稱謂；不收完整生日，生肖由使用者自行確認；先移除原始語音蒐集。
   - 願望紀錄永久預設私人；分析、日誌及崩潰報告不得包含暱稱或願望內容，分析資料匿名且不記錄願望內容。
   - 提供逐筆刪除、全部刪除功能及資料遺失說明；App Store 上架需提供隱私政策網址並如實申報資料處理方式。

## 8. 下一步

上述待確認事項第 1–9 項目前均為【產品假設】或【技術暫定】方向，已反映進架構，但建議在投入 Phase 2 以後的實作前，先完成下方驗證步驟；僅第 8 項（廟宇成長機制細節）本來就留待後續團隊討論再定案，不阻塞 MVP 開發。

**開發前建議的驗證步驟（Phase 0，1–2 週）：**
