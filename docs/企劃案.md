# 心願廟 WishTemple 企劃案（草稿 v0.7）

> 狀態：規劃已定案主要方向，Xcode 專案已建立（Phase 1 骨架）。
> 正式產品名稱：中文「心願廟」／英文「WishTemple」（【產品假設】，見第 7 節第 1 項）；原工作代號 `OnlineTemple` 僅保留為 git 倉儲/資料夾名稱。

## 1. 產品願景

打造一款以台灣民俗信仰文化為基礎的私人數位祈願與文化體驗 iOS app，讓使用者能在手機上進行引導式參拜、許願紀錄，並認識廟宇文化與神明由來；若使用者不想進行線上參訪，也可搜尋附近的實體廟宇並開啟地圖前往。**本產品為完全虛構的「線上廟宇」品牌，不代表任何實體宮廟，不代辦實體宗教儀式，也不保證任何祈福效果；附近廟宇搜尋結果也不代表本產品與該廟宇具有合作、認證或代辦關係**（見第 7 節第 2、10 項）；「安太歲」「點光明燈」等功能名稱沿用民俗慣用語，但實質是使用者的個人數位祈福紀錄，不等同真實宮廟的正式登記。目標是用現代化、視覺化且尊重文化的方式，提供低壓力的私人祈願體驗，同時尊重使用者選擇親自前往實體廟宇的需求。

### 目標受眾（待確認，先列假設）
- 無法常常回廟裡拜拜的信眾（離鄉遊子、忙碌上班族）
- 對民俗信仰文化有興趣、想了解神明由來的年輕族群
- 想幫家人安太歲/點燈但不方便親自到廟的人
- 不認同或不習慣線上參拜、希望尋找附近實體廟宇親自前往的人

## 2. 核心功能

| # | 功能 | 說明 |
|---|------|------|
| 1 | 拜拜 / 許願 | 線上參拜流程（選神明 → 上香/獻供動畫 → 許願文字或語音），純屬個人私密紀錄 |
| 2 | 安太歲（個人數位祈福紀錄） | 依生肖／儀式年度免費建立個人數位安太歲紀錄，僅使用者自己可見，非真實宮廟正式登記；完成後可自願選擇 1／2／3／4 USD 支持開發，略過或未付款不影響紀錄 |
| 3 | 點光明燈（個人數位祈福紀錄） | 選燈位樣式、填寫祈福對象並免費建立當年度個人數位紀錄，僅使用者自己可見，非真實宮廟正式登記；完成後可自願選擇 1／2／3／4 USD 支持開發，略過或未付款不影響紀錄 |
| 4 | 廟宇介紹 | 廟宇沿革、建築特色、參拜須知 |
| 5 | 神明介紹 | 玉皇大帝、月老、媽祖、關公等神明的由來、職掌、祭拜方式 |
| 6 | 廟宇視覺入口 | 廟宇外觀圖，點擊後進入內部場景瀏覽擺設（3D，見第 5 節） |
| 7 | 台灣廟宇建築百科 | 介紹台灣傳統廟宇的建築組成與工法，例如三川殿、龍柱、石獅、屋頂形式（燕尾脊/馬背）、剪黏、交趾陶、藻井、木雕/石雕、門神、匾額對聯等；可搭配 3D 內部場景做互動熱點導覽 |
| 8 | 許願樹 / 許願牌 | 類似日本神社繪馬、首爾塔戀愛鎖的許願牌/鎖，寫下願望後「掛上」個人許願牆或首頁大樹；僅使用者自己可見，不做公開社群牆 |
| 9 | 廟宇成長機制 | 廟宇初期規模簡陋、神明較少，隨使用者完成文化閱讀/免費參拜/定期回顧願望等「文化探索進度」累積，逐步擴建、解鎖更多神明；**不與付費金額掛鉤，避免「花越多越靈」觀感**（新想法，細節待設計，見第 7 節） |
| 10 | 附近實體廟宇 | 使用者不想線上參訪時，可在主動操作後使用目前位置搜尋附近廟宇，依約略直線距離排序，查看名稱、距離與地址，並在 Apple 地圖中開啟地點或規劃路線；搜尋結果來自第三方地圖資料，不代表合作、認證或資訊完整正確（見第 7 節第 10 項） |

## 3. 資訊架構（導覽結構草案）

採用 Tab 導覽，四個主要分頁：

```
TabView
├── 首頁（廟宇）  ── 2D 廟宇視覺入口 + 許願樹（可掛願望牌/戀愛鎖）、公告、快捷儀式按鈕；點擊廟宇進入內部/3D 場景；另設「想親自參拜？尋找附近廟宇」次要入口
├── 儀式          ── 許願 / 安太歲 / 點光明燈 的入口與紀錄
├── 神明百科      ── 神明列表 → 神明詳情（由來、職掌、如何祭拜）；另設「建築百科」子分類介紹廟宇建築組成（龍柱、屋頂、藻井等）
└── 我的          ── 個人祈福紀錄、通知設定、關於廟宇
```

「許願樹/許願牌」傾向規劃為首頁場景中的互動節點（2D 大樹意象），而非獨立分頁；使用者在此瀏覽/管理自己掛上的願望牌（僅個人可見，【產品假設】，見第 7 節第 5 項）。

「附近實體廟宇」不新增第五個 Tab，以免與 App 的私人數位祈願主流程競爭；從首頁次要入口進入獨立搜尋頁，預設以距離排序的清單呈現並可切換地圖。只有在使用者點擊「使用目前位置」時才要求定位權限；若拒絕、受限制或關閉定位，仍可手動輸入地區搜尋。

## 4. 資料模型草案

```
Temple            廟宇基本資料（名稱、簡介、沿革、特色、圖片）——虛構廟宇，不設真實地址
Deity             神明（名稱、別名、由來故事、職掌、祭拜方式、圖片/3D位置錨點）
ArchitectureFeature 廟宇建築元素（名稱、類別如樑柱/屋頂/雕飾、說明文字、圖片、3D位置錨點），例如龍柱、燕尾脊、剪黏、藻井
RitualType        儀式種類 enum（拜拜 / 安太歲 / 點光明燈 / 許願）
WishEntry         許願紀錄（使用者、對象神明、內容、時間）——預設且永久為私人，不提供公開選項
AnnualRitualCycle 儀式年度設定（穩定識別碼、顯示名稱如「2027 丁未年」、開始／結束日期、是否開放）——日期由每年度內容設定提供，不以固定國曆日期寫死
LightLampRecord   光明燈個人數位紀錄（燈位樣式、祈福對象暱稱、儀式年度、建立時間、狀態）——不收生日等真實個資，與支持交易分離
TaisuiRecord      安太歲個人數位紀錄（生肖、儀式年度、暱稱、建立時間、狀態）——與支持交易分離
RitualSupportTier 自願支持固定級距（StoreKit 商品 ID、美國基準價格 1／2／3／4 USD）——四個通用支持商品供兩種年度儀式共用，實際顯示價格由 StoreKit 回傳；原生銷售報表只能依商品 ID 彙總，不能據此區分儀式來源
SupportTransaction 自願支持交易（儀式類型、儀式年度、商品 ID、交易 ID、購買日期、環境、退款／撤銷狀態與日期）——用交易 ID 防止同筆付款重複處理，不作為祈福紀錄完成條件
UserProfile       使用者基本資料（可選暱稱、祈福紀錄關聯）——不收真實姓名
NearbyTempleResult 附近實體廟宇的暫時性搜尋結果（名稱、座標、地址、距離、地圖項目）——與虛構 Temple 分開，不寫入持久化資料庫
```

延續 MVVM 慣例：Model 純資料、Service 負責存取（先用本地 Mock / 之後可接雲端）、ViewModel（`@MainActor`）負責畫面狀態與流程邏輯、View 只做呈現與導覽。

## 5. 技術架構

- **UI**：SwiftUI，MVVM
- **首頁廟宇視覺**：2D 呈現（插畫/圖片素材），包含廟宇外觀與許願樹意象，一般 SwiftUI 排版即可完成，不需要 3D 引擎（【技術暫定】，見第 7 節第 7 項）
- **廟宇內部場景**：點擊廟宇後才進入，使用 RealityKit（依你先前選擇），以 `RealityView` 呈現可環顧的廟宇內部；MVP 階段先用簡化幾何/佔位素材，之後再換上正式 3D 模型與美術資源
  - 內部場景可放置 `ArchitectureFeature` 對應的互動熱點（例如點擊龍柱、屋頂彈出說明卡片），把「台灣廟宇建築百科」內容與 3D 導覽自然結合，規劃在 Phase 4（見第 6 節）
- **服務層**：protocol-backed services，例如：
  - `TempleContentServicing`（廟宇/神明內容）
  - `WishServicing`（許願紀錄存取）
  - `RitualServicing`（安太歲/點燈登記）
  - `NearbyTempleSearching`（附近實體廟宇搜尋，封裝 MapKit/Core Location）
  - 皆搭配 `Mock*` 版本供開發與測試使用
- **持久化**：MVP 先用本地儲存（SwiftData 保存紀錄，UserDefaults 只放設定），資料模型需保留帳號擴充性；之後若要雲端同步紀錄/跨裝置同步，可平滑升級為後端服務（【技術暫定】暫不做帳號系統，見第 7 節第 4 項）
- **金流**：拜拜、許願、安太歲與點光明燈個人數位紀錄全部免費完成；安太歲或點光明燈完成後，可自願透過 StoreKit 消耗型 In-App Purchase 支持開發團隊，四個共用固定級距的美國 storefront 基準價格暫定為 1／2／3／4 USD，不提供自由輸入金額。略過、取消、待處理、失敗或退款均不影響祈福紀錄；所有支持級距也不改變紀錄內容、視覺、燈位、祝福文案、祝福效果或廟宇成長進度。App 內一律顯示 StoreKit 回傳的當地幣別與價格，不硬編碼 USD（【產品假設＋技術暫定】，見第 7 節第 3 項）
- **本地化**：繁體中文 + 英文兩語系架構（【技術暫定】，見第 7 節第 6 項），採字串檔案管理；MVP 內容先以繁體中文為主，其餘語系與完整英文內容日後視驗證結果擴充
- **附近實體廟宇**：使用 Core Location 取得一次性的前景位置，以 MapKit `MKLocalSearch` 在指定區域分別執行「廟宇／宮廟／寺廟／道觀」等可本地化、可經實測調整的自然語言查詢，合併並依地圖項目識別資訊、名稱與座標去重後，再依使用者位置計算約略直線距離排序。原生 MapKit 沒有可單獨涵蓋台灣廟宇的公開 POI 類別，因此名稱關鍵字與地圖分類只用於保守的相關性加權，不以是否包含「廟、宮、壇、寺」等單一字詞硬性排除結果；Phase 2 須以都市、偏鄉及離島樣本驗證前 10／20 筆結果的正確率。搜尋範圍【技術暫定】先採 5 公里，少於 5 筆時依序擴至 15、30 公里，合併去重後最多顯示 20 筆；使用 `regionPriority = .required` 約束 MapKit 回傳區域，並再次以直線距離排除範圍外結果。手動地區搜尋使用 `MKLocalSearchCompleter` 提供鄉鎮市區或地標建議；使用者選取建議後，以 `MKLocalSearch.Request(completion:)` 取得 `MKMapItem` 的座標與區域，作為相同 5／15／30 公里搜尋及排序的中心。自由文字直接搜尋可由 `naturalLanguageQuery` 處理，但正式流程以選取建議為主，降低同名地區、錯字及模糊地名造成的歧義；新實作不採用已被 Apple 標示 deprecated 的 `CLGeocoder.geocodeAddressString`。點擊結果透過 `MKMapItem.openInMaps` 在 Apple 地圖中開啟地點或規劃路線，路線計算、預估時間與導航均由 Apple 地圖提供，WishTemple 不自行提供導航。只申請「使用 App 期間」權限，不使用背景定位、不持續追蹤，也不把位置、查詢或結果寫入本地紀錄、分析事件、日誌或自有伺服器；應支援降低精確度的位置及手動地區搜尋 fallback

## 7. 待確認事項與目前決議

以新創公司內部討論的方式，先針對以下事項推演出目前傾向方向。**這些推演目前僅來自單人分飾多角色的內部討論，尚未經過真實使用者訪談、民俗/宗教顧問審閱，也未做任何互動原型測試**，因此下方一律不再標示「✅ 已決議」，改用以下三種狀態標示，避免團隊誤以為已完成驗證：

- 【產品假設】：內部推演出的方向，需要真實使用者訪談或顧問審閱後才能視為定案
- 【技術暫定】：工程面的暫定做法，可依技術限制或後續需求調整，非商業/文化定案
- 【研究驗證完成】：已透過實際訪談、測試或審閱驗證（目前尚無任何項目達到此狀態）

開發前建議先完成第 8 節下一步中的驗證步驟，再將對應項目升級為「研究驗證完成」。

1. **產品/專案正式名稱** — 【產品假設】傾向：中文「心願廟」／英文「WishTemple」
   - 決策過程（PM／UX／GUI／RD／Sales／Marketing 內部討論）：
     - PM：名稱要能一眼傳達「拜拜＋許願」的核心體驗，且不綁定任何真實宮廟，避免代言/授權疑慮。
     - Marketing：曾提案「拜拜go」，直覺、口語化、本地辨識度高，但偏向工具型 App 語感，且英文「BaiBai」易被誤讀成「bye-bye」，對想強調誠心祈願的品牌調性偏輕佻；也提案「平安廟／PingAn Temple」，但「平安」與知名企業「平安保險 Ping An」撞名，Sales 認為有品牌辨識風險，予以否決。
     - UX：需要中英文都好唸、好拼、好記，「心願廟／WishTemple」兩種語言念起來直覺，不需要額外教育使用者。
     - GUI：「心願」＋「廟」給出明確視覺方向——燈籠、許願牌、廟宇剪影都能自然圍繞「wish」意象發展，也呼應許願樹/許願牌核心功能（第 2 節第 8 項）。
     - RD：確認 `com.wishtemple.*` bundle identifier 未被占用、可直接使用，`WishTemple` 作為 Xcode 專案/Target 名稱在 Swift 中也不與系統框架衝突。
     - Sales：「Wish」在 App Store 搜尋語意上與許願/祈福品類的關聯度高，且與規劃中的「廟宇成長機制」（許願→香火→蓋廟）敘事一致，行銷素材可以直接用「許一個願，蓋一座廟」當 tagline。
   - 結論：定名「心願廟 WishTemple」，決議後已建立對應的 Xcode 專案（見下方）。

2. **內容來源與真實性** — 【產品假設，尚待民俗/宗教顧問審閱】
   - 廟宇為完全虛構的「線上廟宇」品牌，不對應任何特定真實宮廟；此定位需一致反映在第 1 節產品願景、第 2 節功能命名，避免使用者誤解為真實宮廟代辦。
   - 神明由來、故事、職掌等內容，透過公開資料（維基百科、民俗文化資料等）搜尋彙整後改寫。
   - 新增內容範疇：台灣傳統廟宇建築知識（三川殿、龍柱、石獅、燕尾脊/馬背屋頂、剪黏、交趾陶、藻井、木雕/石雕、門神、匾額對聯等），同樣以公開建築/文化資料搜尋彙整後改寫，作為「台灣廟宇建築百科」內容素材（見第 2 節第 7 項）。
   - 待辦：每篇內容需記錄資料來源與授權、作者/編輯、文化顧問、最後審閱日期、地區或派別差異、圖片/音效/字體/3D 模型使用權，並建立勘誤與下架流程；彙整完成後仍需人工審核宗教用詞與建築知識描述是否正確、恰當，避免對特定信仰或文化資產造成誤解或冒犯。

3. **商業模式** — 【產品假設，待測試使用者對付費的理解與意願】
   - 拜拜／上香／許願／安太歲／點光明燈均可免費完成。安太歲或點光明燈完成後，才提供一次可明確略過的自願支持邀請；使用者是否支持及支持金額均不影響紀錄狀態或後續使用。
   - 年度週期：安太歲與點光明燈不是訂閱，不自動續期或扣款。每個儀式年度以年度設定資料提供穩定識別碼、顯示名稱（例如「2027 丁未年」）及開始／結束日期，避免把每年不同的農曆新年日期寫死；週期結束後，紀錄轉入歷年紀錄而不刪除。新年度須由使用者重新主動建立，建立相同「儀式類型＋儀式年度＋祈福對象」時先提示已有紀錄，避免誤建；同年度仍可替不同對象各自建立。
   - 暫定支持級距如下；USD 是美國 storefront 的基準價格，其他地區使用 Apple 自動產生或團隊在 App Store Connect 設定的對應價格：

     | 顯示情境 | 自願支持級距（美國基準價格） | 功能差異 |
     |---|---|---|
     | 完成安太歲年度紀錄後 | 1／2／3／4 USD | 無；未支持與所有支持級距的紀錄、呈現及文案均相同 |
     | 完成點光明燈年度紀錄後 | 1／2／3／4 USD | 無；未支持與所有支持級距的紀錄、呈現及文案均相同 |

   - 自願支持卡片只在祈福紀錄已成功建立後出現；每個「儀式類型＋儀式年度」最多主動顯示一次，即使同年度替多位對象建立紀錄也不反覆彈出。卡片預設不選取任何價位，提供同等清楚的「暫時不要」，並明示「紀錄已完成；是否支持及金額高低都不影響內容或祈福效果」。使用者略過後，仍可從「我的」頁面主動開啟支持入口。
   - 不得以「基本／加持／靈驗／尊榮」、更好的燈位、不同神明、動畫特效或虔誠等級區分級距，也不得用倒數、缺額、厄運或罪惡感文案促購；四個金額選項使用相同視覺權重，不預選較高金額。
   - App 內價格、幣別與稅務後金額只讀取 StoreKit `Product.displayPrice` 等本地化資料，不把 1／2／3／4 USD 硬編碼成所有使用者實際看到的價格。待處理、取消或失敗只影響支持結果，祈福紀錄仍保持完成；介面提供安全返回與由使用者主動重試。
   - 商品暫定為四個由安太歲與點光明燈共用的消耗型 In-App Purchase；每筆已驗證交易保存 `productID` 與唯一 `transactionID`，避免重複處理。若交易退款或撤銷，只更新支持交易狀態，不刪除、降級或撤銷使用者先前免費建立的祈福紀錄；退款逆轉時再恢復支持交易狀態。
   - 商品與分析界線：維持四個通用支持 SKU，不因安太歲／點光明燈拆成八個商品，以符合「支持 WishTemple、不是購買特定儀式」的定位。App Store Connect 原生銷售報表依商品 ID 彙總，因此只能看到各金額級距的購買數與收入，不能區分儀式來源，也不能單獨計算儀式支持轉換率。若 Phase 4 需要比較兩種儀式，須另行評估不含暱稱、願望、位置等個資的最小化分析事件，至少記錄儀式完成、支持頁曝光及已驗證購買三個計數與 `ritualType`，以取得轉換率分母；未建立這套分析前，不得把原生購買數稱為儀式「轉換率」。只有在團隊確認必須直接從 Apple 原生報表區分兩種儀式的購買數與收入時，才改為每種儀式各四檔、共八個 SKU。
   - 技術／合規影響：自願支持依 Apple App Review Guideline 3.1.1 使用 StoreKit；不接外部金流，也不稱為慈善捐款、真實宮廟香油錢或實體宗教服務。正式送審前仍須依上架 storefront 的最新規範核對外部購買連結及價格揭露要求。
   - 因不代辦真實宮廟登記，僅需可選暱稱等象徵性資訊，個資合規範圍大幅降低（見第 7 節第 9 項個資原則）。

4. **帳號系統** — 【技術暫定】
   - MVP 階段不需要登入帳號，使用者拜拜/許願時默念在心裡即可（與實體拜拜體驗一致），資料先以裝置本地儲存（SwiftData，設定另存 UserDefaults）。
   - 架構上保留帳號擴充性：Model 與 Service 層以 protocol 抽象設計，之後要加 Apple 登入 + 雲端同步時可平滑升級，不需重寫資料層。
   - 安太歲／點光明燈紀錄同樣先存在本機；由於紀錄本身免費，刪除 App、換機未移轉或裝置損壞造成的資料遺失不涉及付費功能遭撤銷，但購買前後仍須清楚說明本機資料限制，並提供資料匯出。是否採用 SwiftData + CloudKit 私人資料庫同步，須和願望內容上雲的隱私取捨一併驗證，不因加入自願支持而自動啟用。

5. **許願牆／社群功能** — 【產品假設（縮小範圍為個人版）】
   - 目前只做「個人許願牆」，不做公開社群留言板，避免一開始就要做內容審核機制；願望紀錄永久預設私人，不提供公開選項（見第 4 節 WishEntry 模型）。
   - 視覺呈現參考日本神社繪馬牌、韓國首爾塔戀愛鎖等意象，讓每一次許願變成一個可視化的「牌子/鎖」，掛在使用者自己的許願牆或首頁大樹上。
   - 未來若要做公開/社群版本，可當作獨立的 Phase 5+ 功能再評估（屆時需一併設計審核機制）。

6. **多語系範圍** — 【技術暫定】
   - 先保留繁體中文、英文兩語系的本地化架構（字串檔案管理），但 MVP 內容以繁體中文為主；待驗證海外客群需求後，再投入完整英文內容製作，避免過早投入未經驗證的翻譯成本。

7. **首頁呈現方式與 3D 素材** — 【技術暫定】
   - 首頁採 2D 呈現（廟宇外觀 + 許願樹意象），點擊廟宇後才進入內部場景／3D 視角。
   - 首頁大樹作為「許願樹」節點，可掛願望牌或戀愛鎖造型的許願物件，與廟宇並列在 2D 首頁場景中。
   - 此決定讓 MVP 初期可用一般圖片/插畫素材完成首頁；廟宇內部/建築百科導覽場景建議先用 2D 熱點驗證互動設計，待有使用數據支持後再投資 RealityKit 正式 3D 資產（RealityKit 4 的跨平台 `RealityView` 為 WWDC24 世代能力，若採用需在此明訂 deployment target 與最低裝置，並規劃 2D fallback，詳見第 5 節）。

8. **廟宇成長機制** — 🆕 新想法，待細部設計（Phase 5，不阻塞 MVP）
   - 構想：廟宇初期規模較小、神明數量少，隨使用者完成文化閱讀、定期回顧願望、完成免費參拜、探索建築知識、參與節慶文化活動等「文化探索進度」累積，逐漸解鎖更多神明、擴建廟宇規模，帶來「大家一起把小廟蓋成大廟」的參與感。**明確不與付費金額掛鉤**，避免「花越多越靈」的觀感，也不設排行榜、限時燈位、倒數焦慮或神明稀有度機制。
   - 待討論的細節：
     - 成長基準：全站共用一座會成長的廟（需要後端服務同步），還是每個使用者各自擁有一座（可維持本地儲存）？這會直接影響第 4 節帳號系統與第 5 節持久化的技術選型，需先決定再設計。
     - 成長門檻與階段數：例如分幾個廟宇規模等級，每級對應多少文化探索進度？
     - 美術資源：至少需要對應各成長階段的 2D 首頁場景圖，建議 MVP 先規劃 3 個階段（簡陋 → 中型 → 大廟），3D 內部場景是否同步升級可留待後續評估。
     - 是否搭配「新神明解鎖」故事線（廟越蓋越大才請到某尊神明進駐），會增加內容撰寫需求。
   - 建議：先列為 Phase 5 的加值功能，MVP 以固定規模的廟宇上線，之後再疊加成長機制，避免一開始範圍拉太大。
   - 付費與進度界線：所有成長進度來源都必須有免費取得方式；安太歲／點光明燈的年度免費完成行為可依未來統一規則計算文化探索進度，但自願支持是否購買、購買次數及 1／2／3／4 USD 級距一律不產生或增加進度。同一儀式年度的重複紀錄不得被用來付費加速成長。

9. **個資原則** — 【產品假設，尚待法務確認台灣個資法適用範圍】
   - 不收真實姓名，改用可選暱稱或稱謂；不收完整生日，生肖由使用者自行確認；先移除原始語音蒐集。
   - 願望紀錄永久預設私人；分析、日誌及崩潰報告不得包含暱稱或願望內容，分析資料匿名且不記錄願望內容。
   - 提供逐筆刪除、全部刪除功能及資料遺失說明；App Store 上架需提供隱私政策網址並如實申報資料處理方式。
   - 位置權限、手動地區搜尋及 MapKit／Apple 地圖服務的資料處理另依本節第 10 項規範；隱私政策與 App Store 隱私申報檢查清單必須一併涵蓋該項，不得因位置不寫入本地資料庫就略過審查。

10. **附近實體廟宇** — 【產品假設＋技術暫定，待使用者測試與實機驗證】
   - 產品目的：提供不想、不習慣或不認同線上參訪的使用者一條清楚的實體參拜路徑，而不是把所有人留在虛構線上廟宇中。
   - 入口與流程：首頁以次要卡片顯示「想親自參拜？尋找附近廟宇」；進入說明頁後，由使用者主動點擊才請求定位。成功後顯示依約略直線距離排序的清單，可切換地圖；點選廟宇後顯示名稱、地址、約略距離及「在 Apple 地圖中開啟／規劃路線」。WishTemple 本身不提供路線計算或導航。
   - 權限與替代流程：只要求「使用 App 期間」的位置權限，不要求「永遠允許」或背景定位；拒絕權限、定位受限制、降低精確度、無法取得位置時，仍提供手動輸入鄉鎮市區或地標的搜尋方式。未操作附近搜尋前不在 App 啟動時要求權限；手動搜尋改以所選地區中心作為排序基準，不把該距離標示為「距離你」，避免讓使用者誤以為 App 仍取得其位置。
   - 資料與隱私：位置只用於當次搜尋與距離計算，不建立足跡、不保存最近搜尋、不寫入分析或崩潰日誌，也不傳至自有後端；正式實作與上架前仍須說明 MapKit／Apple 地圖服務的資料處理方式，並在 `NSLocationWhenInUseUsageDescription` 清楚解釋用途。本項須與第 9 項個資原則一併納入隱私政策、App Store 隱私申報及第三方 SDK 資料盤點。
   - 搜尋與篩選策略：原生 MapKit 沒有能單獨涵蓋台灣廟宇的公開 POI 類別；先以「廟宇／宮廟／寺廟／道觀」等多組在地化自然語言查詢取得候選結果，再合併去重並作保守的相關性排序。名稱是否包含「廟、宮、壇、寺」等字詞只作加權參考，不作硬性納入或排除條件；正式查詢詞與排序規則須以不同地區實機結果調整。
   - 搜尋範圍與數量：【技術暫定】先搜尋 5 公里；少於 5 筆時自動擴至 15 公里，再不足時擴至 30 公里，每次顯示目前範圍並允許使用者主動擴大。合併去重後最多顯示距離最近的 20 筆，避免都市結果過多，同時降低偏鄉完全無結果的機率。
   - 資料可信度：結果為地圖搜尋服務提供，可能有遺漏、分類錯誤、地址或開放資訊過期；App 不建立「官方廟宇名冊」，不顯示自行推定的祭祀服務、營業時間或宗派，也不宣稱推薦、認證或合作。介面應提示使用者出發前以廟宇官方資訊確認。
   - 搜尋定義：使用目前位置時，「最近」指目前搜尋範圍內由地圖服務回傳且通過基本相關性排序的候選結果，再依使用者位置計算約略直線距離排序；手動地區搜尋則依所選地區中心排序。兩者都不保證涵蓋所有實體廟宇，也不等同實際步行或行車距離。地點顯示、路線、時間與交通方式交由 Apple 地圖處理。
   - UX 狀態：至少涵蓋首次說明、定位詢問、載入、成功、無結果、網路失敗、定位失敗、權限遭拒／受限制及重新搜尋；權限遭拒時提供前往系統設定與手動搜尋，但不得反覆強迫要求權限。
   - GUI／無障礙：結果頁以清單為主要呈現、地圖為可選模式；卡片需支援 Dynamic Type、VoiceOver、深色模式與足夠觸控區域，距離不可只用地圖視覺或顏色表達。

## 8. 下一步

上述待確認事項第 1–10 項目前均為【產品假設】或【技術暫定】方向，已反映進架構，但建議在投入 Phase 2 以後的實作前，先完成下方驗證步驟；僅第 8 項（廟宇成長機制細節）本來就留待後續團隊討論再定案，不阻塞 MVP 開發。

### 正式開發順序

以下順序以先完成可驗證的核心垂直流程、延後高成本或尚未驗證的功能為原則；Phase 0 的使用者與文化顧問驗證應與低風險的工程基礎並行。

1. **完成 Phase 1 資料骨架（已完成，2026-09-14）**：建立 `WishEntry`、`AnnualRitualCycle`、`TaisuiRecord`、`LightLampRecord`，以及對應的 Service protocol、Mock 實作與基礎單元測試。
2. **建立 SwiftData 儲存層（已完成，2026-09-14）**：已支援願望的新增、查詢、逐筆刪除與全部刪除，並建立版本化 JSON 匯出格式；設定資料維持使用 UserDefaults。
3. **完成第一條 MVP 核心垂直流程**：選擇神明 → 參拜引導 → 填寫願望 → 儲存在本機 → 從「我的」查看或刪除紀錄。
4. **在 UI 實作前完成 UX／GUI 審查**：確認流程、文案、載入／空白／錯誤狀態、Dynamic Type、VoiceOver 與深色模式；清楚揭露「私人數位紀錄，不是真實宮廟代辦」。
5. **補齊核心測試與隱私能力**：涵蓋資料新增、刪除、重複紀錄規則、資料匯出與敏感內容不進入分析或日誌。
6. **開發附近實體廟宇 MVP**：完成定位前說明、手動地區搜尋、漸進式搜尋範圍、距離排序、錯誤 fallback，以及跳轉 Apple 地圖。
7. **驗證成立後再進入商業化與高成本視覺**：Phase 3 實作安太歲／光明燈年度紀錄與 StoreKit 自願支持；正式 RealityKit 3D 素材延後到留存與使用數據足以支持投入時再製作。

**開發前建議的驗證步驟（Phase 0，1–2 週）：**
1. 訪談 15–20 位潛在使用者，確認是否需要「私人、低壓、尊重文化的數位祈願體驗」，以及是否清楚這不是實體宮廟代辦。
2. 訪談 3–5 位民俗、宗教或宮廟實務顧問，審閱神明/廟宇建築內容與宗教用詞。
3. 用互動原型測試 8–10 人，觀察核心流程完成率、對產品性質的誤解率，以及對安太歲／點光明燈完成後四個自願支持級距的理解；確認使用者知道不支持也已完成紀錄，且支持與金額高低都不影響功能或祈福效果。
4. 測試使用者是否願意在 7–14 天內回來再次回顧願望，作為留存假設的初步驗證。
5. 針對不想線上參訪的受訪者測試「附近實體廟宇」入口，確認他們是否能理解定位用途、辨識地圖資料非官方認證，並能在拒絕定位後完成手動地區搜尋；另以都市、偏鄉及離島地點檢查前 10／20 筆結果的相關性、重複率與搜尋範圍擴大行為。
